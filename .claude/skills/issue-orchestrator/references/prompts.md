# 指示文のひな形

`<...>` を埋めて使う。各セッションは会話の経緯を知らないので、指示文だけで作業できるように書く。リポジトリ固有の規則ファイル名（CLAUDE.md、DEVELOPMENT.md、security の文書など）は、実際のリポジトリに合わせて書き換える。

## 目次
1. 実装（独立 PR）
2. 実装（stacked PR の上の段）
3. 敵対的レビュー
4. 指摘への対応
5. 修正の確認

---

## 1. 実装（独立 PR）

```
<owner>/<repo> の Issue #<サブ>「<タイトル>」を実装してください。

## 前提
- 親 Issue は #<親>（設計の合意事項）。まず #<サブ> と #<親> の本文、<現在の仕様のドキュメント> を読んでください。
- このリポジトリの <CLAUDE.md / DEVELOPMENT.md / security の文書> の規則（テストを先に書く、<品質ゲート> 必須、ドキュメントの更新 など）に従ってください。
- ブランチは `<ブランチ名>`。main から切ってください。main 向けの独立した PR にします。

## やること
<サブ Issue の決定済みの方針を要約>

## 実装前に必ずユーザーに確認すること
<未解決の論点。無ければ「設計上の判断が必要になったら、実装前にユーザーに確認してください」>

## 進め方の注意
- 仮説や憶測で実装を進めないこと。<未確認の事実> は実際に確かめ、確認できなければユーザーに相談してください。
- 完了したら push して、main 向けの PR（タイトルは <規約>、本文に `Closes #<サブ>` と `Refs #<親>`）を作ってください。
- PR の監視（subscribe）はしないでください。
```

## 2. 実装（stacked PR の上の段）

`create_session` の `source_revision` に下の段のブランチを指定する。

```
<owner>/<repo> の Issue #<サブ>「<タイトル>」を実装してください。

## 前提
（1 と同じ）

## stacked PR として作る
- この作業は PR #<下の段の PR>（ブランチ `<下の段のブランチ>`）の上に積む、GitHub の stacked pull requests にします。
- ブランチ `<このブランチ>` を `<下の段のブランチ>` から切ってください。
- まず `gh stack --version` を実行し、使えるか報告してください。
- このセッションでは GitHub の GraphQL API が使えないため、`gh stack submit` は使わず次の手順で作ってください。
  1. ブランチを push する
  2. PR を REST で作る。base は `<下の段のブランチ>`
  3. `POST /repos/<owner>/<repo>/stacks` に `{"pull_requests": [<下の段の PR>, <この PR>]}` を渡してスタックとして登録する（既にスタックがあれば `POST /repos/<owner>/<repo>/stacks/<スタック番号>/add` に `{"pull_requests": [<この PR>]}`）
- `<下の段のブランチ>` には push しないでください。下の段に変更が入ったら自分のブランチに取り込んでください。
- この上にさらに積む予定があれば、ブランチ名は変えないでください。

## 実装前に必ずユーザーに確認すること
（1 と同じ。特にセキュリティ設計が関わるものは設計案をまとめて承認を得る）

## 進め方の注意
（1 と同じ。PR の本文に `Closes #<サブ>` と `Refs #<親>`）
```

## 3. 敵対的レビュー

`create_session` の `source_revision` に PR のブランチを指定する。

```
<owner>/<repo> の PR #<n>「<タイトル>」（Issue #<サブ>、親 #<親>）を、敵対的にレビューしてください。

## 目的
この PR がマージされたら壊れる・危ない・仕様と違う、という点を見つけることです。「問題なさそう」と確認するためのレビューではありません。

## 前提
- 読むもの：PR の差分と本文、Issue #<サブ> と #<親> の本文、<リポジトリの規則>、<関連する仕様・セキュリティの文書>
- （stacked PR の上の段なら）レビュー対象は #<n> の差分（#<下の段> からの差分）だけです。

## 観点
<PR の性質に合わせて具体的に。例>
- 正しさ：境界値、エラー時の挙動、並行処理、タイムアウト、失敗時の後始末
- セキュリティ：外部入力がシェル・引数・パス・URL・HTML のどこかで解釈し直されないか、他サイトからのリクエスト、既知の過去の問題の再発
- 仕様との食い違い：#<親>・#<サブ> の合意事項
- テスト：実装を戻したら本当に落ちるか、欠けている組み合わせ
- ドキュメントの更新漏れ

## 進め方
- 指摘はできるだけ実際に再現・実行して確かめてから出してください。コードを読んだだけの指摘は、そう明記してください。推測だけの指摘は出さないでください。
- 指摘は PR の該当行へのインラインコメントで投稿してください（pending review を作成 → 行コメントを追加 → `COMMENT` で submit）。重大度（🔴 必ず直す / 🟠 直すべき / 🟡 任意）を先頭に付け、再現手順・影響・修正案を書いてください。<言語> で書いてください。
- 各コメントの末尾には、区切り線と `_Generated by [Claude Code](https://claude.ai/code)_` を付けてください。
- まとめ（submit 時の本文）には、指摘の件数と、確認して問題がなかった範囲を書いてください。
- コードの変更・コミット・push・PR の作成はしないでください。PR の監視（subscribe）もしないでください。
```

## 4. 指摘への対応（実装セッションへ、Routine で送る）

```
PR #<n> に<敵対的レビュー / 修正確認>の指摘が付きました。対応してください。
- <重大度> `<ファイル:行>`：<指摘の要約>
- （自動レビュー bot の指摘があれば）<bot 名>（<優先度>）`<ファイル:行>`：<要約>
- ほかに未解決のスレッドや新しいコメントがないかも、PR 全体を確認してください。
- 各指摘を実際に確かめ、正しければテストを先に書いて直し、<品質ゲート> を通してから push してください。誤り・対応しない場合は、そのスレッドに理由を返信してください。直したものは修正コミットを示して返信し、スレッドを resolve してください。
- 設計判断が必要なものは、実装前にユーザーに相談してください。
- （stacked PR の土台なら）このブランチは stacked PR の土台です。ブランチ名は変えず、rebase・force push はしないでください。
- （stacked PR の上の段なら）`<下の段のブランチ>` には push しないでください。
- PR の監視（subscribe）はしないでください。
```

## 5. 修正の確認（レビューセッションへ、Routine で送る）

```
PR #<n> の実装側が、レビュー指摘に対応して `<コミット>`（<コミットメッセージ>）を push し、<k> つのスレッドに返信しました。修正を確認してください。
- 対象：<指摘の一覧（自動レビュー bot の分も含める）>
- 最新の head を git fetch して確認してください。可能なものは、前回と同じく再現手順をもう一度実行して確かめてください。
- （設計が変わった点があれば）<何が変わったか>。その新しい動作に新しい問題がないかも見てください。
- 結果を各スレッドに返信してください（確認済み／不十分とその理由・再現手順）。不十分なら unresolve してください。
- 修正で新たに生じた問題があれば、新しいインラインコメントとして投稿してください（重大度付き）。
- 各コメントの末尾には、区切り線と `_Generated by [Claude Code](https://claude.ai/code)_` を付けてください。
- コードの変更・コミット・push はしないでください。PR の監視（subscribe）もしないでください。
```
